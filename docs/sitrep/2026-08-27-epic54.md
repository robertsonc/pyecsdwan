## The endpoint that wasn't

`GET /flow/{neId}/q`, named in the original issue for both flow commands,
exists in **neither** vendored spec. It is an `EC_SD-WAN_Expert` internal URL
shape — the same class of error as epic #4's `/route_policy`, `/nat_policy`
and `/vrf_snat_maps`, which turned out to be pyedgeconnect module names.

The real endpoint is `GET /flow`, and it is better than the issue assumed:

- `ipEitherFlag` matches an address at **either end, server-side**, so
  `show flow <ip>` needs no client-side filtering at all.
- The response carries a computed `active` summary block alongside the rows.
- `nePk` and `maxFlows` are both **required** — omitting `maxFlows` is a 400,
  not a default.

That reshaped #59 before a line was written, which is the whole point of
verifying first.

## The shared foundation, and the bug in my own first draft

`reports/fanout.py` was written and merged before any brief went out — the
same pattern as `specs.py` last epic. All five commands fan out per-appliance,
and left alone that becomes five ad-hoc thread pools.

**The obvious implementation has a bug that makes its own timeout
decorative.** `with ThreadPoolExecutor(...)` joins every worker on `__exit__`,
so a hung appliance stalls the whole report even though each individual wait
timed out. I measured it rather than reasoning about it: **3.00s with the
context manager, 0.20s with `shutdown(wait=False, cancel_futures=True)**,
against a 3-second straggler. There is a test pinned to exactly that case.

Second bug in the same draft: keying success off a non-None value silently
drops rows for endpoints that legitimately answer `null`. `Outcome.done` now
distinguishes "returned None" from "never ran".

All five mock endpoints landed in **one** commit rather than four, because
`mock/server.py` conflicted on every parallel merge in the previous two epics.
That worked — no worker touched it except to add `mask1`/`mask2` support.

## A fixture of mine that asserted nothing

I seeded `/gms/versions` with `installed[0] == current`. So an implementation
rendering `installed[0]` as "the Orchestrator version" — the exact mistake the
brief warned about, and the one the spec's own summary line ("Returns
available orchestrator versions") invites — **passed every fixture-based
assertion**.

The #57 worker found it, correctly left the shared file alone (three workers
were reading it) and pinned the semantic in a test instead. Fixture fixed
after that merge: `installed[0]` is now a newer staged release, which keeps it
realistic (a real Orchestrator does have its running version installed) while
making the mistake fail here rather than ship.

**A fixture that cannot fail is not a fixture.** Worth checking the next one
the same way.

## Corrections from workers

**#58 — my cost model was inverted.** I asked whether per-overlay summary
reads could replace counting flow rows, framing row-counting as the expensive
path. It is the cheap one: `active` carries no per-overlay breakdown, so a
per-overlay tally needs one request per *(appliance × overlay)* — strictly
more than the one-per-appliance call that already returns the rows. Two
further findings, both verified:

- The `overlays` filter takes overlay **IDs** separated by `|`, not names.
- `overlayName` is *"Inbound and outbound overlay name. E.g. 'overlay1 |
  overlay2'"* — one row can name two overlays, so a per-overlay tally
  double-counts and column totals would exceed the appliance total.

**#56 — `/broadcastCli` cannot be the multi-appliance path.** Its 200 is
`text/plain: string` (the GUID), and this repo's own
`docs/research/appliance-config.md` already recorded "no per-appliance status
from broadcastCli". Shipped instead: bounded `fan_out` over per-appliance
`POST /cli`, with `--broadcast` available and labelled execution-status-only.

*One line of that justification was overstated and I corrected it at merge:*
`/action/status` does carry a `result` field — "Opaque blob of data related to
action. Typically, this is the result of the action." So broadcast output is
**unverified, not disproven**. The conservative default is right either way.

**#56 also refused `debug` verbs**, which I had asked for. That namespace is
not read-only: `DELETE /debug/generic/{type}` deletes a module's data and
`GET /oro/debug/closeGrpcConnection` mutates behind a read-shaped verb. Both
verified. Deny-by-default says refuse rather than guess which are inert.

**#55 — `GET /deployment?nePk=` as I wrote it does not work.** Both `nePk`
*and* `cached` are required — the same trap `/appliancesSoftwareVersions`
carries — and the mock implements no orchestrator-scope `/deployment` at all,
so using it would have shown every appliance unreachable and failed the
report's first acceptance criterion. `resources/deployment.py` reads the same
object over the appliance proxy, which is what "reuse the resource read paths"
actually pointed at.

## The allowlist (#56)

The one surface in this epic that opens a path to an appliance's command
interpreter, so the allowlist was the deliverable and printing the easy part.

`validate_command()` accepts only if: non-empty and ≤200 chars; **every
character** is in a positive alphabet (`A-Za-z0-9`, space, `-_./:`); no empty
element when split on `" "`; `tokens[0] == "show"` or `"display"` compared
with `==`, never `startswith`; and at least two tokens.

The character whitelist does the load-bearing work — `;` `&` `|` `\n` `\r`
`\t` `\0` ESC VT FF backtick `$` `(` `)` `>` `<` quotes `\` `!` `?` `*` `#`
and **every non-ASCII codepoint** fall outside it, so NBSP / U+2028 / U+2029 /
U+3000 / U+0085 / BOM / ZWSP cannot pose as the separator between a verb and
its argument. The command is **never normalized**: anything needing a strip to
pass is refused, so the validator and the appliance cannot disagree about what
ran.

40 refusal cases, with the non-ASCII ones written as `\uXXXX` escapes —
a literal NBSP in a test file is invisible in review, which is exactly what
makes it a good attack and a bad test.

## Follow-up taken after the epic

`GET /vrf/config/securityPoliciesSegments` lists every configured
`<src>_<dst>` pair in one call and takes no parameters. #55 derived the pairs
from the segment cross product instead — O(n²) GETs, bounded at 16 — because
the mock did not implement it and the demo fabric would have printed a
degradation note on every run. That was the only blocker, so the mock route
was added and the report now takes the endpoint, with the cross-product
derivation kept as the fallback for releases that lack it.

One thing I got wrong on the way: I announced the new path with a note on the
section. `notes` is what makes a section report as *degraded*, so a success
message marked the un-degraded case as degraded. Removed.

## What is NOT verified

- **`ipEitherFlag`.** The spec's description says *"If true, ip1 will be
  treated as the source IP"* — directional matching, the opposite of what the
  parameter name means and of what both the implementation and the mock
  assume. One of the two is wrong and **nobody has tested it live.** If the
  description is right, `show flow <ip>` silently misses every flow where the
  queried address is the destination. Confirm before trusting it on a
  production fabric.
- Neither the `securityPoliciesSegments` path nor its fallback has run against
  real gear. The mock implements the endpoint as this repo reads the spec,
  which is not the same as the vendor implementing it that way.
- Unchanged from prior epics: every write path from epics #3 and #4 is
  spec-confirmed but has never executed against real gear.

## A refactor I attempted and reverted

The four report renderers belong in `cli/render.py` — that module's own
docstring says it holds the presentation-only helpers shared by the
subcommands and the shell, which is exactly what they are, and the shell
currently imports them back out of `main.py`.

I started the move and reverted it. The four public functions are 178 lines
but pull **13 more symbols** with them, plus `err_console` (a `main.py`
object), and `render.py` would have to import `pyecsdwan.reports` while
`main.py` already imports both — the import graph needs checking for a cycle
first. That is a refactor, not a move. Recorded in `docs/futures/README.md`
with the full symbol list so the next person starts informed rather than
discovering it the same way.
