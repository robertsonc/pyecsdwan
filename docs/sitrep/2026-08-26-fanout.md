## Lane-planning notes for next time

- **The "append-only, don't reorder" instruction for `resources/__init__.py`
  doesn't survive contact with `ruff`'s `I001`/`RUF022`.** Multiple workers
  independently discovered this and worked around it differently (comment-
  only touches with `noqa`, or literal alphabetical insertion). Next
  session: either tell workers to run `ruff --fix` and not worry about
  placement, or add a `per-file-ignores` entry for this one file so the
  instruction can be followed literally. Either way, expect this file to
  conflict on nearly every parallel PLUGIN merge regardless — that's fine,
  the conflicts are trivial and `git rerere` learns the resolution shape
  after the first one or two.
- **`mock/server.py` conflicts were also trivial but not zero-effort.** Every
  wave saw 1 conflict in this file (two workers' new fixture/route blocks
  landing at the same insertion point after `_seed_zone_list_meta()` or
  similar). Worth considering: give each worker an explicit, distinct
  insertion anchor (e.g. "append immediately before the `# -- state --`
  section comment, after the last existing `# -- end <kind> --` marker") to
  cut this to zero next time, rather than the current "append a labeled
  block" instruction which several workers interpreted as the same
  location.
- **Grounding against live gear before writing worker briefs paid for
  itself.** Every plugin this session shipped with real, live-captured
  payload shapes baked into its docstring and mock fixtures, not
  best-guesses from SDK docstrings alone — and it caught real surprises
  (deployment's `vifs` key, appliance-scope zones having no Default/id-0
  row, the DHCP subtree living inside `deployment` rather than needing its
  own endpoint). If live access is available again, spend the 10-15 minutes
  probing before writing briefs — it measurably improved worker output
  quality and cut down on "unverified" caveats.
- **Session-branch-as-trunk adaptation worked cleanly.** The literal fanout
  brief assumes merging into local `main` and pushing there; this
  environment's harness rules require developing on the assigned
  `claude/pyecsdwan-burndown-e6v9km` branch with a single PR instead. Worker
  worktrees branched off the current session-branch head (not `main`) so
  each wave started from the previous wave's merged state — this meant Wave
  B workers could `read` (not import) already-merged Wave A code as
  reference (`#13` reading the real, merged `deployment.py`), which produced
  better-grounded output than reading a brief's description alone would
  have. Recommend keeping this pattern.
